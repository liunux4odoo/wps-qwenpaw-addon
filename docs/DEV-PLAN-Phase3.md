### P1. 启动时 WPS 桥连接错误误报（右上角状态）

- **现象**：插件启动时显示"WPS 桥连接错误"，但对话开始后就正常了
- **根因（已核实）**：`WPS_POLL_PORT`（原 :58891）是 **wps-mcp 懒启动端口**——QwenPaw 首次调 WPS 操作工具前不监听。加载项轮询客户端在启动时连不上 = **预期行为**（ARCHITECTURE.md §3.2 明确："重连中是预期行为，工具调用后自动连上"）。但 UI 显示"错误"是误导
- **方案（FE）**：
  1. WPS 桥状态**不再显示为"错误"**，改为"未连接（等待首次操作）"或直接隐藏
  2. WPS 桥接状态移到**右上角**，与连接状态**合并显示**（一个状态区：ACP 连接 + WPS 桥，两级状态）
  3. 状态文案区分三态：`连接中`（启动握手）/ `就绪`（对话可用）/ `WPS 未激活`（对话可用但 WPS 操作未就绪，等待首次操作）
- **验收**：启动加载项，右上角显示"就绪"或"WPS 未激活"（**不是**红色"错误"）；发消息后自动变为"就绪 + WPS 已连接"

### P2. 对话中断无输出（输入框/发送按钮不可用）

- **现象**：对话过程中突然中断，输入框和发送按钮不可用，界面没有任何输出
- **现状核实（已诊断，2026-09-03）**：
  1. **bridge 下行永久断（真中断，已独立方案）**：`bridge/acp-bridge.py:378 _stdout_reader` 用 `readline()` 读 qwenpaw 输出，asyncio 默认 64KB 行缓冲——工具大返回值（如 `getActiveDocument` 文档全文）作为单行 JSON 超限抛 `ValueError` → reader 任务崩溃 → 下行永久断 → 60s 看门狗触发。**修复方案已落盘** `docs/plan-2026-09-03-bridge-stdout-reader-fix.md`（本项 FE 部分依赖该 bridge 修复先落地）。
  2. **看门狗阈值过短（慢响应误报，本次验证结论）**：qwenpaw 在**单次请求内**存在真实 thinking 完全静默窗口——实测 17:30:50 prompt 发出后 17:31:21→17:32:52 **91s 零下行**（qwenpaw 内部在推理/规划工具调用，不吐 thinking 也不发文本，静默结束后立刻发起 5 个 `request_permission` 继续干活）。全局活跃段内此类静默最大 **78s / 91s / 104s**。**当前 60s `P2_NO_FIRST_CHUNK_MS` 必然误报**。
  3. **thinking 心跳被忽略**：qwenpaw 思考时会密集下发 `agent_thought_chunk`（bridge 日志 12325 次，密集时每 0.1-0.2s 一条），但 main.js `onAcpSessionUpdate` **没有 `agent_thought_chunk` 分支**，thinking 心跳不被 `touchActivity()` 接收 → 无法用来续命。
- **方案（FE + 诊断，含 D 错误恢复引导）**：
  1. **接住 thinking 心跳（续命信号）**：`onAcpSessionUpdate` 增加 `agent_thought_chunk` 分支 → `touchActivity()`（重置看门狗）+ 可选"正在思考…"打字指示器。覆盖 thinking 密集场景（大多数）。
  2. **看门狗阈值分层**（实测证明 60s 不够）：
     - `P2_NO_FIRST_CHUNK_MS`（无首 chunk）由 60s **提到 120s**——覆盖 91s 静默 + 余量
     - `P2_ACTIVITY_MS`（无任何下行）由 120s **提到 180s**
  3. **自动延长（超时触发时不死判）**：看门狗触发时**不直接判死**，进入"疑似中断"状态——UI 显示"AI 仍在处理…"提示 + **自动顺延**（如再等 60s），顺延上限 2-3 次（总等待 ≤ 5min）。顺延期间任何下行（thinking/文本/工具审批）→ 回到正常状态；达到上限仍无下行 → 才判定中断。
  4. **兜底恢复**：判定中断后自动重置 UI 状态（恢复输入框），提示"对话中断，已重置，请重试"；不静默卡死
  5. **错误可见 + 可操作（D）**：任何 ACP 错误/断连都渲染为可见错误卡片，带**可操作按钮**——"重试"（重新发当前消息）/"重建会话"（session/close + session/new）；文案友好（不说"内部错误"，说"连接中断，可重试或重建会话"）
- **验收**：
  1. 人为制造中断（kill qwenpaw acp / 断 bridge），UI 在超时后自动恢复输入框 + 显示可操作错误卡片（含重试/重建按钮，点击有效）
  2. **长思考不误报**：复现 90s+ 静默场景（如让 qwenpaw 处理需长时间规划的 prompt），UI 不判死——显示"AI 仍在处理…"并自动顺延，静默结束后正常输出
  3. **thinking 心跳生效**：qwenpaw 思考期间（有 `agent_thought_chunk` 下行），即使无文本 chunk，看门狗也不触发
  4. 正常对话无回归

### P3. agent id 改为插件页面选择 + 记住上次选择

- **现象**：现在 agent id 是运行 bridge 时通过命令行参数指定的（`--agent ai-developer`）
- **方案（FE + BRIDGE）**：
  1. bridge 支持 `--agent` 缺省 + 插件在初始化时上报所选 agent
  2. 插件页面（侧边栏设置区或首次进入引导）提供 agent 下拉选择，从 bridge 查询可用 agent 列表
  3. **记住上次选择**：localStorage 持久化，下次进入自动选中
  4. agent 切换 = 重建 ACP session（session/close 旧 → session/new 新）
- **验收**：插件页面可选 agent；刷新/重启后记住上次选择；切换后对话上下文正确切换

### P4. AI 过程呈现：折叠开关 + 思考反馈（含 B/C）

- **现象**：AI 思考过程和工具调用以系统消息形式平铺显示，刷屏；AI 思考期间反馈弱（只有状态条文字"处理中…"）
- **方案（FE，含 B 思考反馈 + C 工具调用可视化）**：
  1. 工具栏加"显示过程"开关（默认折叠或默认显示，用户可配，localStorage 持久化）
  2. 思考/工具调用过程折叠为一条摘要行（如"🔧 调用了 3 个工具 · 查看"），点击展开细节
  3. **工具卡片（C）**：工具调用渲染为结构化卡片——工具名 + 目标文档 + **结果状态（ok/失败 + 摘要）**；失败时卡片红色、可点击看详情；不展开原始 JSON
  4. **思考反馈（B）**：AI 响应期间显示打字指示器（三点动画或"思考中…"占位），并有阶段切换提示（"正在调用工具" / "正在生成回复"），而非只有一个静态状态条文字
- **验收**：开关切换生效并持久化；默认状态不刷屏；工具卡片显示结果状态、失败可展开看错误；AI 响应期间有打字指示器 + 阶段切换可感知

### P5. 中止执行

- **现象**：AI 思考/执行过程中无法打断，只能等它完成
- **方案（FE + ACP 只读）**：
  1. 输入区/消息区在 AI 响应期间显示"停止"按钮
  2. 点击后发 ACP cancel（需确认 qwenpaw acp 支持 `session/cancel` 或等价方法；若协议不支持，退化为"丢弃后续流式输出 + 重置 UI"）
  3. 停止后输入框恢复可用，可继续发新消息
- **验收**：AI 长响应/长工具链执行时点"停止"，UI 立即恢复可交互；qwenpaw 侧不再有新输出

### P6. 上传文件/图片（原样给 qwenpaw，含 G 粘贴图片）

- **现象**：目前只能纯文本对话，无法给 AI 看文件/图片
- **方案（FE + BRIDGE + ACP 待验证，含 G 粘贴图片）**：
  1. 输入区加"添加附件"按钮（文件/图片选择）+ **粘贴图片识别**（G）：粘贴板有图片时识别为待上传附件
  2. **关键未知点（待验证 V1）**：QwenPaw 的 ACP `session/prompt` 是否支持多模态 content（图片/文件）？`session_mcp.py` 只看到文本；需实测或查 QwenPaw ACP schema。**若支持**：文件/图片 base64 原样传给 qwenpaw；**若不支持**：阶段 3 先做"文件内容提取成文本"（前端读取 text/表格/图片 OCR 类不做），图片先占位不实现
  3. 附件在消息区渲染为缩略/文件卡片
- **验收**：能上传文件/图片（含粘贴图片），qwenpaw 能看到内容（或明确降级为文本提取）；附件在对话中可见

### P7. 进入插件自动展开侧边栏

- **现象**：用户进入插件时侧边栏是收起/需要手动展开状态
- **方案（FE + MANIFEST 待验证）**：
  1. 检查 WPS 加载项是否有"自动展开 taskpane"的 API/配置（`window.Asc.plugin.resizeWindow` 或 manifest 选项）
  2. 若有：加载时自动 `resizeWindow` 到默认宽度
  3. 若 WPS 不支持自动展开：改为引导提示（首次进入显示"点击功能区按钮展开侧边栏"）
- **验收**：打开文档进入插件，侧边栏自动展开到可用宽度（或确认平台限制后给引导）

### P8. 不同文档侧边栏内容隔离（按文档隔离，含 G 会话历史）

- **现象**：不同文档的侧边栏内容一模一样，没有按文档隔离
- **根因**：架构决策"文档即会话"（one doc = one session）已定，但 **UI 状态没有按 session 隔离**——多个文档可能共用同一个 taskpane 实例的 DOM/消息列表
- **方案（FE + BRIDGE 确认，含 G 会话历史/多轮上下文）**：
  1. 确认 WPS 中不同文档是否**共享同一 taskpane 实例**（若是，侧边栏是同一个 DOM，需要按当前激活文档切换会话上下文；若不是，天然隔离）
  2. 若共享：消息列表/输入状态按 `session_id`（文档 id）隔离——切换文档时显示对应会话的历史，互不串台
  3. 会话历史可从 bridge/qwenpaw 查询（`session/load`），或前端按文档 id 缓存
  4. **多轮上下文（G）**：同一文档内连续追问时保持会话上下文，用户不用重复描述文档内容（依赖会话历史正确加载 + 切换）
- **验收**：文档 A 的对话历史不会出现在文档 B；切换文档显示各自上下文；同文档连续追问可引用前文

### P9. excel/ppt 未加载插件

- **现象**：只有 word 能加载插件，excel 和 ppt 没有
- **现状核实**：需确认 WPS 加载项 manifest 的加载作用域（是否只注册了 word 应用？还是 excel/ppt 需要不同 manifest/注册）
- **方案（MANIFEST + 待诊断）**：
  1. 检查 `manifest.xml` / 注册方式（`~/.local/share/Kingsoft/wps/jsaddons/`）是否限定了文档类型
  2. 若限定：为 excel（wps/et）和 ppt（wps/wpp）补注册；确认 WPS 的加载项机制是否按应用类型隔离
  3. 验证：分别用 et/wpp 打开文档，侧边栏能加载
- **验收**：word/excel/ppt 三类文档都能加载插件（或明确记录平台限制）

### P10. Markdown 渲染升级（A）

- **现状**：消息区用 `textContent` 纯文本渲染，AI 回复的 Markdown（代码块/表格/列表/加粗）全部原样显示
- **方案（FE）**：
  1. 引入轻量 Markdown 渲染（零依赖优先：自写 mini-renderer 或内联成熟实现，项目零依赖约束下**不引外部库**需评估；候选：`marked` 单文件版可 vendored 进仓库，或实现子集）
  2. 渲染子集：标题/加粗/斜体/列表/代码块/行内代码/表格/链接——覆盖 AI 回复 90% 场景
  3. 代码块高亮（可后置，批 3）
  4. **安全**：Markdown 渲染必须转义 HTML（AI 回复可能含 `<script>` 等，禁止 `innerHTML` 直插未经转义内容）
- **验收**：AI 回复中的代码块/表格/列表/加粗正确渲染；含 HTML 标签的回复不执行/不注入

### P11. 操作结果反馈（E）

- **现状**：文档操作（插入/替换/改格式）完成后只有侧边栏一行纯文字"已完成"，用户在文档里找不到改在哪
- **方案（FE，受 wps-bridge 边界限制，依赖 V6）**：
  1. **侧边栏反馈**：操作成功后消息区显示结构化反馈（操作类型 + 位置 + 影响范围，如"✅ 已替换 3 处"）
  2. **文档内定位（可选增强）**：wps-bridge 已支持 `getDocumentTextByRange` 等定位工具——在可行范围内，操作后把光标/选中区定位到修改处（需确认 wps-bridge 是否已有"定位"命令，无则加轻量命令，属阶段 2 扩展边界，需回 ARCHITECTURE.md 确认）
  3. **高亮（备选，依赖加载项能力）**：AI 修改段落加背景色（架构隐藏优势之一），MVP 可不做
- **验收**：操作后侧边栏有结构化结果反馈；定位/高亮如实现则验收，否则记录为已知边界

### P12. 视觉打磨（F）

- **现状**：`css/taskpane.css` 148 行基础蓝白样式（#2b579a），纯聊天布局
- **方案（FE）**：
  1. 视觉层次：圆角卡片式消息气泡、阴影、间距系统
  2. 状态色语义化：成功/警告/错误/信息 四色一致
  3. 过渡动画：消息出现、状态切换（轻量，不炫技）
  4. 空状态：无消息时显示引导（"试试：把'foo'改成'bar'"）
  5. 主题：先不做多主题，保持单主题打磨到位
- **验收**：视觉层次清楚、状态色语义一致、无消息时有引导空状态；动画不干扰操作

### P13. 快捷指令（G 独立部分）

- **现状**：输入区是单一 textarea，无快捷命令
- **方案（FE）**：
  1. **MVP 只做 `/clear`**：清空当前会话（含 session 重建或前端清空，按会话管理边界定）；输入框识别 `/` 开头的指令
  2. 预留扩展：`/help`、`/doc` 等后续再加（阶段 4）
- **验收**：`/clear` 可清空当前会话；未知指令给提示不报错

### P14. 清除对话历史（用户补充）

- **现象/需求**：用户希望能显式清除对话历史（不仅是 `/clear` 命令，而是页面上的清除入口）
- **与 P13 的关系**：P13 的 `/clear` 是"快捷指令"，本项补的是**明确的 UI 入口**（如设置区/会话区"清空对话"按钮 + 确认弹窗）
- **方案（FE + BRIDGE 确认）**：
  1. 会话区/设置区加"清空对话"按钮，点击弹确认（防误触）
  2. 清空动作 = 前端清空消息列表 + **后端侧处理**（按会话管理边界二选一：a. `session/close` + 重新 `session/new`，彻底重置；b. 若 qwenpaw 支持清空 session state 则复用，需确认 ACP 是否有等价接口——**目前 ACP 无 `session/clear`，V7 待验证**）
  3. 清空后：输入框恢复、空状态引导显示、文档隔离状态（P8）同步清
- **验收**：点"清空对话"→ 确认 → 消息清空、AI 不再记得之前内容（可验证：清空后问"我刚才说了什么"应无记忆）；误触有确认弹窗

### P15. 同一文档加载历史对话记录（用户补充，已核实与 ACP 关系）

- **需求**：重新打开同一文档时，能加载之前的历史对话记录（用户可见）
- **核实结论（2026-09-03，已读 qwenpaw 源码）——不重复，但"历史"有两层**：

| 层 | 谁存 | ACP 能拿到吗 | 用途 |
|---|---|---|---|
| **AI 上下文记忆**（语义） | qwenpaw session state（JSON 落盘，key=session_id + user_id=`acp_{session_id[:8]}` + channel=""） | ✅ `session/load` 自动恢复 | AI 记得之前聊过什么 |
| **前端显示历史**（消息明文） | ACP 协议**不暴露拉取接口**（server 方法只有 new/load/list/resume/close/prompt/cancel/set_session_model/set_config_option；`list_sessions` 只返回 id/cwd/title） | ❌ 拿不到明文 | 用户要看到之前聊过什么 |

  - **不重复的原因**：`session/load` 恢复的是**后端 AI 记忆**（架构决策 2"文档即会话"下，重开文档自动恢复语义上下文）；"前端加载历史对话记录"是**前端 UI 显示层**，ACP 拿不到消息明文，必须前端自己处理。两者互补：AI 记得但用户看不见 = 割裂；用户看得见但 AI 不记得 = 误导。
  - **关键约束**：MVP 下"历史对话显示"**只能靠前端自己缓存**（localStorage 按文档 id），因为 ACP 无拉取接口、且 bridge 铁律"不实现会话管理、不碰 qwenpaw 内部存储"（ARCHITECTURE.md §6.1）
- **方案（FE）**：
  1. 前端按文档 id 缓存消息历史（localStorage：`key = doc_id`，value = 消息数组）
  2. 打开文档时：先查前端缓存 → 渲染历史消息 → 再 `session/load` 恢复 AI 记忆（语义层已自动，前端只需对齐 session id 与文档 id）
  3. 消息渲染与 P15 一致（P10 Markdown）；清空（P14）时同步清前端缓存
  4. **可选增强（不做，除非用户要求）**：扩展 bridge 读 qwenpaw session state JSON 拿明文——**不推荐**，违反 bridge 铁律，且耦合 qwenpaw 内部存储格式
- **验收**：重开同一文档，历史消息可见（来自前端缓存）；AI 仍记得之前上下文（`session/load`）；清空对话后缓存同步清；不同文档历史互不串（配合 P8）
- **待验证**：V7（前端缓存方案下无需 ACP 接口；若未来要"跨设备/跨桥"历史，需确认 qwenpaw 是否有官方读取途径）
